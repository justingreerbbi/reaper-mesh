# Message acceptance and delivery draft v1

Independent message identities and radio packet definitions are separate from USB/config versions. Initial hard bounds: 1,024 UTF-8 bytes per nonempty text, eight device message records, eight non-evicting owner sequence marks per boot, 32 client history entries, one pending upload per client. Config and message commands have separate ID namespaces. All traffic is plaintext/unauthenticated until encryption is designed.

USB submission uses 32-byte binary chunks encoded as at most 64 lowercase hex characters, avoiding large per-field embedded buffers and allowing UTF-8 code points to cross chunk boundaries. At most 32 chunks, indexed from zero; every nonfinal chunk contains exactly 32 bytes. Whole-text UTF-8/control validation occurs before queue acceptance. A message binds its request ID, origin boot, channel, destination, chunk count and immutable contents. Conflicting duplicates are rejected without changing the original message. Partial assembly expires after five seconds; queued/delivery work expires after sixty seconds. Expiry never reopens an ID for execution.

Device states: receiving, queued, transmitted, acknowledged, failed, rejected, unknown. Queued acknowledges only volatile local queue acceptance. Transmitted means radio adapter accepted all fragments as sent, not delivery. Acknowledged means the addressed destination accepted the complete message; it is never human-read status. Broadcast destination `broadcast` never produces recipient acknowledgments. Until radio integration, hardware queues expire without transmission. No client or simulator may claim RF delivery from USB acceptance.

A status carries the request ID, current state, received-chunk bitmap, optional stable message ID, and reason. Recovery uses a distinct read-only query; it never replays upload chunks after a link change. Message records and owner high-water marks survive logical USB reconnect but not device reboot. Old-boot outcomes remain unknown even if matching text is observed. A new message ID combines the collision-resistant boot identity and monotonic device counter. Finite terminal records may be reclaimed, but non-evicting high-water marks prevent duplicate execution after receipt eviction.

Mandatory checks: chunk reorder/duplication/conflict, invalid UTF-8, maximum size, assembly timeout and exact timeout boundary, queue/owner exhaustion, receipt eviction, lost acceptance and reconnect query, reboot ambiguity, ACK/timeout races, broadcast ACK refusal, no repeated state regression, and bounded client retry budgets. Real mesh packets/forwarding and RF hardware qualification are separate gates.

## Confirmed broadcast completion

A complete transmitted receipt for a broadcast is terminal for the sender: there is no destination ACK to wait for. The client preserves that fact across the observation deadline, disconnect, receipt eviction and journal reload. It does not promote unknown or merely queued broadcasts to transmitted. Unicast transmitted remains unconfirmed until destination ACK/failure, and unfinished work still restores as unknown. A regression covers the broadcast distinction; the UI labels it Broadcast transmitted · no recipient acknowledgment.
